# Базовый уровень безопасности

Этот репозиторий участвует в формировании базового уровня безопасности в рамках родительской задачи Trelio 543.

## Сообщение об уязвимости

## Область, архитектура и доверительные границы

`aida_functions` — внутренняя Dagster code location для отчётов и уведомлений
Aida. Она читает разрешённые данные из PostgreSQL и Dodo API/Pyrus/Zveno,
формирует отчёт и публикует payload в RabbitMQ для доставки ботами. Публичного
входящего HTTP endpoint у компонента нет; Dagster gRPC и RabbitMQ относятся к
внутреннему контуру.

Ответы внешних API, записи БД и параметры manual job считаются недоверенными
до проверки схемы и области доступа. Административный доступ выполняется
только по пути AWG → bastion с TOTP → ресурс с персональным ключом. VLESS в
административный контур не входит.

## Данные и секреты

Компонент обрабатывает идентификаторы аккаунтов и точек, подписки,
операционные показатели, разрешённые данные Pyrus/Zveno и содержимое
сформированных отчётов. Источники — PostgreSQL и внешние API; получатели —
авторизованные пользователи Aida через Telegram/MAX-ботов.

Секретами являются реквизиты PostgreSQL и RabbitMQ, Dodo/Pyrus/Zveno
credentials и сервисный доступ к дешифрованию Dodo-токенов. Значения хранятся
только в Kubernetes Secret или защищённом окружении и не включаются в Git,
логи или этот документ. Доступ имеют назначенные владельцы; ротация
обязательна после утечки, отзыва доступа, потери устройства или смены
интеграции. Сроки хранения и удаление задаются централизованным реестром
данных Aida; данные не хранятся дольше цели обработки.

## Модель угроз и OWASP Top 10

Для внутренней Dagster/gRPC code location без browser DOM XSS и cookie-based
CSRF неприменимы. SSRF, IDOR, небезопасная десериализация, инъекции и
остальные категории сохраняют применимость:

| OWASP Top 10:2025 | Применимость и основные меры |
| --- | --- |
| A01 Broken Access Control | Выборка ограничивается разрешёнными аккаунтами и точками; сервисные действия выполняются с минимальными правами |
| A02 Security Misconfiguration | Закрытый внутренний контур, Kubernetes Secret, минимальные настройки контейнера и Trivy config |
| A03 Software Supply Chain Failures | Dependabot, Trivy, SBOM, закреплённые Actions и проверка точного container image |
| A04 Cryptographic Failures | Dodo credentials зашифрованы, чувствительные данные запрещены в логах; для Pyrus проверка TLS-сертификата настраивается `PYRUS_VERIFY_SSL`, но значение по умолчанию `false`, поэтому production должен явно установить `true`, а живая конфигурация требует отдельного evidence |
| A05 Injection | Параметризованный SQLAlchemy/ORM, валидация API-ответов и payload, Semgrep |
| A06 Insecure Design | Явные trust boundaries, разделение job/resource и отсутствие публичного endpoint |
| A07 Authentication Failures | Сервисная аутентификация интеграций, минимальные права и MFA/TOTP для административного доступа |
| A08 Software or Data Integrity Failures | Проверка схем API/RabbitMQ, SBOM и связь отчётов с commit/image |
| A09 Security Logging and Alerting Failures | Корреляционные идентификаторы, редактирование чувствительных полей, Loki и Alertmanager |
| A10 Mishandling of Exceptional Conditions | Ограниченные timeout/retry, изоляция ошибки одного запроса, безопасные ошибки и runbook |

## Безопасная эксплуатация и инциденты

- изменения выполняются через Pull Request с независимым ручным review;
- после нового commit изменившийся diff проверяется повторно;
- прямой и force-push в `main` запрещены; merge выполняет тимлид;
- при компрометации остановить соответствующий job, отозвать или ротировать
  credential, сохранить минимальное evidence и уведомить владельцев;
- после восстановления проверить логи, очередь и алерты, зафиксировать
  причину и корректирующие действия.

## Автоматические проверки

| Проверка | Назначение | Блокирующее условие |
| --- | --- | --- |
| `Security / AITriage` | Детерминированные встроенные проверки AITriage | Профиль политики `standard`; любая активная находка уровня Critical или High |
| `Security / Semgrep` | SAST-анализ исходного кода с зафиксированными community rules | Находки уровня `ERROR` в категории `security`, а также ошибки сканера или правил |
| `Security / Gitleaks` | Поиск секретов в диапазоне pull request или во всей истории Git | Любая находка; обнаруженные значения полностью скрываются в отчёте |
| `Security / Trivy` | Уязвимости зависимостей, ошибки конфигурации IaC/Docker/GitHub Actions и CycloneDX SBOM | Находки уровня High или Critical |
| `Security / Evidence` | Сводные статусы, версии инструментов, метаданные запуска и SHA-256 артефактов | Отсутствующий или неуспешный результат любого сканера |

Bandit намеренно исключён. Сканирование секретов в Trivy также отключено, поскольку за эту проверку отвечает Gitleaks.

AITriage и Trivy формируют доказательные артефакты CycloneDX SBOM. Workflow записывает репозиторий, commit и версию компонента в SBOM от AITriage, а также сохраняет метаданные базы уязвимостей Trivy, использованной плановой CVE-проверкой.

Workflow запускается для pull request, push в основную ветку, ручного запуска и по еженедельному расписанию со сдвигом времени. Он использует GitHub token только для чтения, не сохраняет учётные данные checkout, фиксирует сторонние Actions по commit SHA, а версии сканеров и контейнерные образы — по digest.

Отчёты сохраняются как артефакты GitHub Actions на 90 дней. Ошибка сканера остаётся ошибкой и после загрузки артефактов; недоступный инструмент никогда не считается успешной проверкой.

## Обновление зависимостей

Dependabot настроен для используемых в репозитории экосистем пакетов, Dockerfile при их наличии и GitHub Actions. Обычные minor- и patch-обновления группируются. Обновления безопасности остаются отдельными от обычных групп обновления версий.

После слияния этой ветки в настройках репозитория или организации также необходимо включить Dependabot alerts и автоматические обновления безопасности.

## Решение по DAST

DAST неприменим к этому code location в текущем развёртывании. Он предоставляет внутренний Dagster gRPC и выполняет исходящие обращения к API и RabbitMQ, не имея публичной входящей HTTP-поверхности.

## Сборка контейнера и проверка образа

В репозитории пока нет автоматизированного набора unit-тестов. Поэтому обязательный контейнерный workflow собирает приложение и компилирует каждый Python-модуль внутри точного образа перед сканированием. Он создаёт CycloneDX SBOM образа и полный отчёт по HIGH/CRITICAL и блокирует исправимые находки HIGH/CRITICAL. После успешного завершения основного scanner workflow для того же commit релиз публикует в существующий GHCR-репозиторий только проверенный образ с commit SHA и очищенным release tag; тег `latest` не публикуется.

## Исключения

Это изменение не добавляет широких исключений по правилам или путям. Если присутствует `.gitleaksignore`, он содержит только точные fingerprints исторических находок; такие записи не отменяют необходимость ротации значения, которое когда-либо являлось настоящим credential. Каждое исключение должно содержать:

- точное правило или fingerprint;
- причину, по которой находка является false positive или принятым риском;
- ответственного;
- дату окончания или пересмотра;
- компенсирующую меру.
